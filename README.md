# Согласование и выполнение заявок на продление

Самостоятельное приложение по заданию `Fullstack_практическое_задание.pdf`. Только вымышленные данные; два изолированных пространства Alpha и Beta. Исходный симулятор включен без изменений, референс извлечен из PDF в [docs/reference_renewals.png](docs/reference_renewals.png).

## Инструменты и стек

Проверено на Windows x64: Node.js **24.17.0**, npm **11.13.0**, Python **3.11.9**, PostgreSQL **18.6**. Нужны Node.js 24+ и Python 3 в PATH. Docker необязателен.

- React 19.3, TypeScript 6.0, Vite 8.3, TanStack Query 5.
- Node.js, Fastify 5, Zod 4, `pg`, PostgreSQL 18. SQL и явные транзакции позволяют видеть границы блокировок и атомарности.
- `node:test` для API и базы. Тесты используют настоящий PostgreSQL, а сценарий восстановления — неизмененный Python-симулятор.
- npm workspaces, строгая типизация, ESLint, Prettier, проверка направлений FSD-импортов. Точные версии зависимостей зафиксированы в `package-lock.json`; воспроизводимая установка — `npm ci`.

## Запуск

Все команды выполняются из корня репозитория. Четыре терминала для базы, симулятора, приложения и разовых команд.

```powershell
npm ci
Copy-Item .env.example .env
```

Терминал 1: локальный PostgreSQL без Docker. Пакет `embedded-postgres` запускает настоящий сервер PostgreSQL, сохраняющий данные в `.data/postgres`. Первое скачивание бинарников требует доступа к интернету и разрешенных npm install-скриптов.

```powershell
npm run db:local
```

База доступна на `127.0.0.1:5433`, пользователь `renewals`, пароль `renewals_local`, база `renewals`. Порт 5433 выбран, чтобы не занимать стандартный 5432. Вместо локального сервера можно использовать Docker Compose:

```powershell
docker compose up -d --wait db
```

Используйте один из этих двух способов. Для собственной установки PostgreSQL укажите `DATABASE_URL` в `.env`.

Терминал 2: симулятор из задания. Дополнительные Python-пакеты не требуются.

```powershell
python provider_simulator.py
```

Он слушает `127.0.0.1:8091`. **Во время проверки восстановления не перезапускайте симулятор:** его операции хранятся только в памяти.

Терминал 3, после готовности базы:

```powershell
npm run db:migrate
npm run db:seed
npm run dev
```

Откройте **http://localhost:5173**. Vite проксирует `/api` на `127.0.0.1:3001`; фоновой обработчик запускается внутри процесса API. Для корректной проверки Origin используйте именно `localhost`, как в `APP_ORIGIN`. Миграции версионируются и выполняются под транзакционной advisory-блокировкой. Seed можно повторять: он не меняет существующие данные и сроки.

Сборка и запуск готового приложения без Vite:

```powershell
npm run build
```

Измените в `.env` `APP_ORIGIN=http://localhost:3001`, затем выполните:

```powershell
npm start
```

Откройте http://localhost:3001. API раздает собранные HTML/CSS/JS. Миграции и seed запускаются отдельно, автоматически база не изменяется. Не запускайте одновременно dev-API и собранный API на одном порту.

## Тестовые аккаунты

Общий демонстрационный пароль: **`Demo-2026!`**. На экране входа выберите аккаунт и введите пароль.

| Логин             | Пространство | Права                                                     |
| ----------------- | ------------ | --------------------------------------------------------- |
| `initiator.alpha` | Alpha        | Просмотр, создание                                        |
| `approver.alpha`  | Alpha        | Просмотр, согласование, отклонение, повтор                |
| `initiator.beta`  | Beta         | Просмотр, создание                                        |
| `universal.alpha` | Alpha        | Обе роли; нельзя согласовать/отклонить собственную заявку |

Сервер определяет права и пространство по учетной записи. Пароли хешируются scrypt с индивидуальной солью. Случайная 256-битная сессия хранится в HttpOnly, SameSite=Strict cookie на 8 часов; в БД хранится SHA-256 токена. Выход отзывает сессию в БД. `localStorage` для токенов не используется. Для локального HTTP `COOKIE_SECURE=false`; при HTTPS установите `true`. Login ограничен 20 запросами в минуту с одного IP. Изменяющие браузерные запросы проверяют Origin. Запросы к API из CLI без Origin разрешены при действующей сессии.

## Данные и состояния

| ID ресурса | Пространство | Название    | Начальный срок | Стоимость, копейки |
| ---------- | ------------ | ----------- | -------------- | ------------------ |
| `res-a-01` | Alpha        | Хранилище A | 2027-03-01     | 128000             |
| `res-a-02` | Alpha        | Сервис B    | 2027-05-20     | 250000             |
| `res-b-01` | Beta         | Сервис C    | 2027-06-01     | 150000             |

Валюта всегда RUB. Стоимость — PostgreSQL `integer`, даты — `date`; парсер `pg` возвращает календарные даты строками `YYYY-MM-DD`, без преобразования в часовой пояс.

| В API        | В интерфейсе     | Допустимый переход                                       |
| ------------ | ---------------- | -------------------------------------------------------- |
| `pending`    | На согласовании  | `processing` или `rejected`, другой согласующий          |
| `rejected`   | Отклонена        | Терминальное состояние                                   |
| `processing` | Выполняется      | `completed` или `attention`, обработчик                  |
| `completed`  | Завершена        | Терминальное состояние                                   |
| `attention`  | Требует внимания | `processing`, согласующий нажимает «Повторить обработку» |

Снимок прежнего срока, нового срока (+30 календарных дней), стоимости и валюты фиксируется при создании. При согласовании срок и стоимость повторно сверяются с ресурсом под блокировкой. Изменение означает 409 и отсутствие задачи отправки. API изменения ресурса не предусмотрено заданием; проверка устаревшего снимка выполняется тестами через БД. Автор, согласующий и время определяются сервером; история записывается в той же транзакции, что и переход. Внутренние события обработчика также видны в истории.

## Как исключены дубли и восстанавливаются операции

1. Частичный **уникальный индекс** `one_active_renewal` разрешает ровно одну заявку ресурса в `pending`, `processing`, `attention`. Он защищает и от параллельного создания, и от прямой записи в БД.
2. Согласование блокирует заявку `FOR UPDATE`. Проверка снимка, переход в `processing`, история и одна строка `renewal_jobs` сохраняются одной транзакцией. Первичный ключ задачи — ID заявки. Параллельное/повторное согласование получает 409.
   При создании, согласовании и завершении блокировки берутся в едином порядке: сначала ресурс, затем заявка. Это исключает инверсию блокировок при одновременном создании и завершении/согласовании.
3. Ключ операции **`renewal:<UUID заявки>`** создается один раз и сохраняется в БД. Для всех POST используются этот ключ и неизменное тело из снимка: `resource_id`, `period_months: 1`, `amount_minor`, `currency: "RUB"`.
4. Перед POST в БД сохраняются счетчик попыток и время следующего выполнения. После неопределенного ответа, в том числе 503/таймаута/ошибки сети/невалидного результата, обработчик ждет `RETRY_DELAY_MS`. Сначала он делает GET по URL-кодированному ключу. Если подтверждения нет, повторяет POST с тем же ключом и телом, до трех POST в одном цикле. GET не расходует бюджет.
5. После третьего неопределенного POST выполняется еще одна отложенная проверка GET. Если подтверждения нет, заявка становится `attention`; новая заявка ресурса остается заблокированной. Ручной повтор сбрасывает только бюджет текущего цикла, сохраняя ключ, снимок и общий счетчик. Он также сначала проверяет результат прежней операции.
6. Результат проверяется по схеме, `status=completed`, `started_count=1`, ресурсу, периоду, сумме и валюте. Подтвержденный ID провайдера, `completed`, **фиксированная новая дата**, завершение задачи и история сохраняются одной транзакцией. Дата присваивается из снимка, к текущей дате никогда повторно не прибавляется 30.
7. Конкурирующие обработчики используют session advisory lock на ID задачи. Блокировка сохраняется на время HTTP, но SQL-транзакция во время сети не открыта. После падения процесса PostgreSQL освобождает блокировку. Время выполнения, счетчики и задача остаются в БД; следующий процесс продолжает с GET. Повторная обработка завершенной задачи ничего не меняет.

Гарантия одного внешнего эффекта опирается на идемпотентность предоставленного провайдера. После перезапуска самого симулятора его память исчезает: проверять прежнюю неопределенную операцию после этого нельзя. При аварии строго между записью счетчика и фактической отправкой POST попытка консервативно считается израсходованной; потерянный бюджет восстанавливается ручным повтором, ключ не меняется.

## Проверка сценария с перезапуском

Используйте свежую базу и свежезапущенный симулятор. До начала `GET http://127.0.0.1:8091/stats?resource_id=res-a-01` должен возвращать `operation_count: 0`. Для новой проверки не удаляйте рабочие данные: можно создать отдельную пустую базу и указать ее `DATABASE_URL`. Автоматические тесты сами создают изолированные базы.

1. В `.env` установите `RETRY_DELAY_MS=30000`. При обычной работе значение по умолчанию — **15000 мс**, таймаут HTTP — **3000 мс**, опрос очереди — **500 мс**. Перезапустите API после изменения конфигурации.
2. Войдите как `initiator.alpha`, создайте заявку для `res-a-01`. Срок пока **01.03.2027**. Ресурс исключен из доступных в форме новой заявки; повторное создание через API возвращает 409.
3. Выйдите и войдите как `approver.alpha`. Откройте вкладку «Заявки», «Подробнее», «Согласовать», «Подтвердить». Два параллельных согласования проверяются автоматически командой `npm test`.
4. В истории дождитесь сообщения «Подтверждение не получено. Результат неизвестен; проверка запланирована». **В течение 30 секунд** остановите только приложение (Ctrl+C в терминале `npm run dev`). Базу и симулятор оставьте работающими.
5. Запустите `npm run dev` снова. После сохраненного времени следующей проверки заявка станет «Завершена». Срок ресурса — **31.03.2027**. Авторизация сохраняется в PostgreSQL.
6. В деталях заявки раскройте «Данные операции» и скопируйте ключ `renewal:<UUID>` — это реальный стабильный ключ данной заявки, а не ID ресурса. В PowerShell:

```powershell
$operationKey = 'renewal:ВСТАВЬТЕ-UUID-ЗАЯВКИ'
$encodedKey = [uri]::EscapeDataString($operationKey)
Invoke-RestMethod "http://127.0.0.1:8091/renewals/$encodedKey"
Invoke-RestMethod 'http://127.0.0.1:8091/stats?resource_id=res-a-01'
```

Ожидаются `started_count=1`, тот же `operation_id`, `operation_count=1` по всем ключам ресурса. Еще один перезапуск приложения не меняет срок.

7. Для `res-a-02` создайте и отклоните заявку. Срок останется **20.05.2027**, `GET /stats?resource_id=res-a-02` вернет 0; история покажет отклонение.
8. Войдите как `initiator.beta`: виден только Beta. Попытки чтения/изменения Alpha по известным ID возвращают 403. Создайте заявку как `universal.alpha`: собственные действия согласования и отклонения заблокированы сервером.

Для ручной проверки `attention` запустите приложение с `PROVIDER_URL=http://127.0.0.1:1` и `RETRY_DELAY_MS=1000`. После трех POST и последнего GET появится «Требует внимания». Верните `PROVIDER_URL`, перезапустите API, войдите согласующим и повторите обработку. Прежний ключ останется прежним.

## Контракты API

Базовый путь `/api`. JSON, cookie `session`. Неавторизованный запрос — 401, отсутствие права/доступа к существующему пространству — 403, неизвестный ID — 404, конфликт состояния/снимка/активной заявки — 409, невалидные данные — 400. Ошибка имеет вид `{ "message": "Понятное описание" }`. Поля роли, автора, сроков или стоимости в изменяющих запросах не принимаются. Формат ID заявки — UUID, ресурса — строка.

| Метод и путь                  | Тело / результат                                                                    |
| ----------------------------- | ----------------------------------------------------------------------------------- |
| `GET /health`                 | Проверка подключения к БД, `{status:"ok"}`; без авторизации                         |
| `POST /auth/login`            | `{login,password}` → пользователь и HttpOnly cookie                                 |
| `GET /auth/me`                | Текущий пользователь: `id,name,workspace_id,workspace_name,can_create,can_approve`  |
| `POST /auth/logout`           | Отзыв сессии, `{ok:true}`                                                           |
| `GET /resources`              | Массив ресурсов текущего пространства, включая `active_request_id`, `active_status` |
| `GET /resources/:id`          | Ресурс: `id,workspace_id,name,expires_on,amount_minor,currency`                     |
| `GET /renewals`               | Массив заявок пространства, новые первыми                                           |
| `GET /renewals?resource_id=…` | История заявок конкретного ресурса с проверкой доступа                              |
| `POST /renewals`              | Только `{resource_id}` → созданная заявка, HTTP 201                                 |
| `GET /renewals/:id`           | Заявка, `history`, `post_attempts`, `cycle_attempts`, `next_attempt_at`             |
| `POST /renewals/:id/approve`  | Пустое тело или `{}` → `{id,status:"processing"}`                                   |
| `POST /renewals/:id/reject`   | Пустое тело или `{}` → `{id,status:"rejected"}`                                     |
| `POST /renewals/:id/retry`    | Пустое тело или `{}` → `{id,status:"processing"}`                                   |

Заявка содержит `id,resource_id,workspace_id,created_by,approved_by,status,old_expires_on,new_expires_on,amount_minor,currency,operation_key,provider_operation_id,created_at`. Списки/детали дополнительно содержат `resource_name,creator_name`. История: `id,actor_name,from_status,to_status,message,created_at`. Для фоновых событий автор отображается как «Фоновый обработчик». Даты календаря — `YYYY-MM-DD`, времена — ISO 8601. Подробные TypeScript-контракты находятся в `packages/contracts/src/index.ts`.

## Проверки

```powershell
npm run typecheck
npm run lint
npm run format:check
npm test
npm run build
npm audit
```

`npm test` самостоятельно поднимает временный PostgreSQL на **55432**, симулятор на **18091**, а в проверке перезапуска — API на **13001**. Проверяются права, 401/403, изоляция по известным ID, подмена автора/ролей, собственное согласование/отклонение, одновременное создание, уникальный индекс БД, параллельное согласование, снимок, отклонение, настоящее принудительное завершение процесса после 503, восстановление с прежним ключом, статистика провайдера, однократное изменение даты, внимание после трех попыток, ручной повтор и конкурирующие обработчики. Рабочая база не затрагивается.

## Архитектура и FSD

```text
apps/web/src/
  app/                  точка входа, QueryClient, общие стили
  pages/                login, workspace; композиция сценариев
  features/             auth, create-renewal, review-renewal
  entities/             session, resource, renewal: модели, запросы, статус
  shared/               api, lib, ui
apps/api/src/
  modules/              auth, renewals, provider, worker
  db/                   подключения, транзакции, миграции, seed
  shared/               ошибки, раздача собранного интерфейса
packages/contracts/     общие типы HTTP-контрактов
apps/api/migrations/    SQL-миграции и ограничения
```

Фронтенд импортирует только нижние слои и public API слайсов через `index.ts`; cross-imports слайсов одного слоя отсутствуют. Компоненты таблиц и деталей локальны странице; отдельный слой widgets без потребности не добавлен. Контракты не содержат серверных зависимостей или исполняемой бизнес-логики. `npm run lint` дополнительно проверяет структуру импортов. FSD применяется к интерфейсу; на сервере использованы предметные модули, соответствующие ответственности и транзакционным границам.

Запросы TanStack Query автоматически обновляются раз в 2 секунды, изменения инвалидируют соответствующие данные. При смене аккаунта запросы отменяются, данные предыдущего пользователя удаляются. Интерфейс содержит состояния загрузки/ошибки/пустых списков, видимый фокус, нативные модальные диалоги с удержанием фокуса, управление вкладками стрелками/Home/End. На мобильной ширине строки таблицы отображаются карточками. Действия подтверждаются; ошибки API и история показаны пользователю.

## Конфигурация и ограничения

Настройки перечислены в `.env.example`: `DATABASE_URL`, `PORT`, `APP_ORIGIN`, `PROVIDER_URL`, `PROVIDER_TIMEOUT_MS`, `RETRY_DELAY_MS`, `WORKER_POLL_MS`, `WORKER_ENABLED`, `COOKIE_SECURE`. Файл `.env` не хранится в Git. Для проверки атомарной постановки можно запустить API с `WORKER_ENABLED=false`, согласовать заявку, затем включить обработчик и перезапустить.

Секреты, cookie, тела запросов, ключи операций и полные ответы провайдера не записываются в логи. В логах API — метод, путь без query string, статус; во внутренних ошибках — только код. Сведения об операции доступны авторизованным пользователям в деталях заявки для приемки.

Это локальное тестовое приложение: один пользователь закреплен за одним пространством; нет регистрации, SSO, уведомлений, редактирования ресурсов, пагинации и собственного брокера. Очередь использует PostgreSQL, обрабатывается последовательно небольшими порциями; этого достаточно для трех ресурсов. Session advisory locks требуют прямого соединения с PostgreSQL, не PgBouncer в transaction pooling. Временные сессии отфильтровываются по сроку, отдельная очистка истекших записей не реализована. Реальное развертывание, мониторинг и внешние аккаунты выходят за границы задания. Обязательные сценарии реализованы; публикация удаленного репозитория требует выбранного пользователем хостинга и доступа к нему.

TypeScript: `strict`, `noUncheckedIndexedAccess`, `noImplicitReturns`, запрет неиспользуемых объявлений и fallthrough. ESLint анализирует типы прикладного кода (`recommendedTypeChecked`), запрещает неявно небезопасные операции с `any`, непроверенные Promise и ошибки React Hooks. Проверка FSD контролирует слои, public API и относительные импорты. Конфигурация браузерных тестов и CI в проект не входят.
