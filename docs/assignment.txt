ПРАКТИЧЕСКОЕ ЗАДАНИЕ / FULLSTACK
Согласование и выполнение
заявок на продление
Разработка небольшого приложения с разграничением доступа и интеграцией с тестовым
API
Формат: самостоятельное приложение в отдельном репозитории.
Время: предварительный ориентир 24-40 часов; практического замера не проводилось, срок
согласовывается заранее.
Стек: TypeScript, React, Node.js / NestJS, PostgreSQL. Разрешены подходящие библиотеки и LLM.
Задача
Пользователи ведут учет ресурсов с ограниченным сроком действия. Чтобы продлить ресурс, сотрудник
создает заявку, другой сотрудник ее согласовывает, после чего приложение отправляет операцию
внешнему сервису.
Разработайте этот процесс целиком: интерфейс, API, хранение и интеграцию. Провайдер в задании
тестовый: он иногда возвращает ошибку после того, как операция уже выполнена. Система должна
корректно обработать такую неопределенность и не выполнить продление дважды.
Границы
 • Используйте только вымышленные данные. Реальные компании, доступы, деньги и внешние аккаунты
 не нужны.
• Регистрацию, SSO, уведомления, развертывание и собственный брокер сообщений реализовывать не
 требуется. Фоновый обработчик можно запустить вместе с приложением.
• Если не успели закончить, сдайте работающий результат и укажите незавершенные пункты. В README
 объясните ключевые решения, ограничения и способы проверки кода.

02 / БИЗНЕС-ПРОЦЕСС
Заявка на продление
Инициатор выбирает ресурс своего пространства и создает заявку. Продление в этом задании всегда
составляет 30 календарных дней от текущей даты окончания ресурса. Сумма и прежняя/новая даты
фиксируются в заявке при создании.
Состояние
Переход
На согласовании
Создана инициатором. Другой пользователь с правом согласования может одобрить
или отклонить.
Отклонена
Завершена без обращения к провайдеру и без изменения ресурса.
Выполняется
Согласована. Задача отправки сохранена и может выполняться фоновым
обработчиком.
Завершена
Провайдер подтвердил операцию; срок ресурса обновлен один раз.
Требует внимания
Подтверждения нет после трех попыток. Результат может быть неопределенным;
повтор использует тот же ключ операции.
Правила
 • Согласующий не может одобрить или отклонить собственную заявку, даже если у него есть обе роли.
 Создатель и согласующий определяются сервером.
• У одного ресурса может быть не больше одной активной заявки: на согласовании, выполняется или
 требует внимания. Не допускайте обхода правила параллельными запросами; закрепите его на уровне
базы.
• Повторное согласование или недопустимый переход возвращает 409. Отклоненная заявка не меняет
 срок; после завершения допустимо создать новую.
• При согласовании проверьте, что срок и стоимость ресурса не изменились относительно снимка заявки.
 Иначе верните 409 и не отправляйте операцию провайдеру.
• Записывайте в историю автора, время и переход состояния. Не записывайте секреты и полный ответ
 провайдера в логи.

03 / ИМИТАТОР ПРОВАЙДЕРА
Тестовое API
Файл provider_simulator.py приложен к PDF и предоставляется отдельно. Запуск: python3
provider_simulator.py. Требуется Python 3, дополнительные пакеты не нужны. Сервер слушает
127.0.0.1:8091.
Приложение обращается к POST /renewals. В заголовке Idempotency-Key передается стабильный ключ
конкретной заявки. Тело запроса:
{
  "resource_id": "res-a-01",
  "period_months": 1,
  "amount_minor": 128000,
  "currency": "RUB"
}
В этом тестовом period_months = 1 обозначает условный период из 30 дней. Имитатор не меняет срок
ресурса в вашей базе: это делает ваше приложение после подтверждения результата.
Запрос
Ответ имитатора
Первый POST с новым ключом
Операция сохранена, но ответ HTTP 503: результат для клиента
неопределен.
Повторный POST с тем же ключом и телом
HTTP 200, прежний operation_id и status=completed; новая
операция не создается.
Тот же ключ с другим телом
HTTP 409, операция не меняется.
GET /renewals/{ключ}
HTTP 200 и результат либо 404, если ключ неизвестен. Ключ в
URL должен быть закодирован.
GET /stats?resource_id=res-a-01
HTTP 200 и operation_count: число всех созданных операций для
этого ресурса.
GET /health
HTTP 200, если имитатор запущен.
Операция в ответе содержит operation_id, status, started_count и исходные поля. started_count равен 1 для
сохраненной операции. Имитатор хранит данные только в памяти: при его перезапуске операции исчезают. При
проверке восстановления перезапускайте приложение, оставляя имитатор работающим.

04 / НАДЕЖНОСТЬ
Выполнение и восстановление
 • Согласование заявки и постановка задачи на отправку должны сохраняться атомарно. Если приложение
 перезапустить после согласования, задача не теряется и может быть продолжена.
• При 503 результат операции неизвестен. Повторите запрос с тем же ключом и телом либо проверьте
 результат по GET. Несколько HTTP-запросов допустимы; у имитатора должна остаться одна операция.
• После подтверждения провайдера запишите результат, состояние заявки и новый срок ресурса одной
 транзакцией. Повторная обработка не должна второй раз сдвигать срок.
• При параллельном согласовании одной заявки допускается только один успешный переход; второй
 запрос получает 409. Дубликат задачи или внешней операции возникать не должен.
• Если после трех попыток POST результат не удалось определить, покажите состояние «Требует
 внимания»; запросы GET не считаются попытками POST. Разрешите согласующему повторить
обработку с тем же ключом. До разрешения результата новая заявка на этот ресурс недоступна.
Граница гарантии. В этой проверке защиту от повторного внешнего эффекта обеспечивает
идемпотентность тестового провайдера. Не требуется обещать такое поведение для произвольного
стороннего API.
Что важно проверить
Предусмотрите настраиваемую задержку после 503 перед проверкой GET или повторным POST, чтобы
можно было остановить приложение до следующего запроса и запустить снова. После перезапуска оно
должно получить прежний результат имитатора и завершить заявку без повторного продления.
Значение задержки и способ проверки опишите в README.
Формат собственных endpoint и фоновой обработки выберите сами. Описать контракты и ограничения
можно в README или OpenAPI.

06 / ПРИЕМКА
Контрольный сценарий
Начните с ресурса res-a-01 в пространстве Alpha: срок 01.03.2027, стоимость 128 000 копеек. Имитатор
свежезапущен, операций еще нет; не перезапускайте его во время сценария.
 • Инициатор Alpha создает заявку. Она находится на согласовании, а срок ресурса пока не меняется.
 Вторая активная заявка на этот ресурс отклоняется.
• Инициатор Beta не получает доступ к ресурсу или заявке Alpha по известному ID. Универсальный
 пользователь не может согласовать собственную заявку.
• Другой согласующий Alpha одобряет заявку. Два параллельных одобрения не создают две задачи;
 повторное одобрение возвращает 409.
• Первая отправка провайдеру создает операцию, но возвращает 503. Остановите и запустите
 приложение. Оно восстанавливает задачу, использует тот же ключ и получает сохраненный результат.
• Заявка становится завершенной, а срок ресурса равен 31.03.2027. Повторная обработка не меняет дату.
 GET по ключу возвращает started_count=1; GET /stats?resource_id=res-a-01 показывает
operation_count=1, в том числе для других возможных ключей.
• Отклоненная заявка не отправляется провайдеру и не изменяет срок. Для другого ресурса статистика
 имитатора остается равной 0. Ошибки и результаты видны в интерфейсе и истории.
Автоматические проверки
Добавьте воспроизводимые тесты бизнес-переходов, прав и изоляции пространств, повторного /
параллельного согласования, восстановления после неопределенного ответа и однократного
изменения срока. Тесты должны проверять поведение API и базы, а не только отдельные
вспомогательные функции.
В README укажите, как воспроизвести сценарий с перезапуском, какой ключ операции использовать
для проверки имитатора и какие решения вы приняли для защиты от дублей.
